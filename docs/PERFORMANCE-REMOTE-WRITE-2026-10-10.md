# Prometheus 远程写入响应与等待预算

日期：2026-10-10。后端基线 `3a3d4b5`，开发分支 `codex/remote-write-budget`。

## 问题与变更

`PrometheusProvider.Write` 同时用于记录规则与拨测指标写入。原实现使用 `io.ReadAll(resp.Body)` 读取错误响应，忽略读取错误，再把全部正文拼入错误；HTTP client 的 timeout 来自数据源，零值时没有整体网络期限。慢或超大的错误响应可能持续占用上一批的拨测槽位，以及记录规则的查询槽位。

- 错误响应最多读取 **64 KiB + 1 字节**用于判定是否超限。小响应保留原状态码/正文诊断；超限明确报错，不回显整段大正文，不返回成功。此限制针对应用读取的响应体，不代表 TCP/HTTP 内部缓冲或对端发送量严格等于该值。
- 保留读取错误的包装链，可用 `errors.Is` 判断取消、截止及异常 EOF；关闭响应体。原先读取失败会丢失原因的用例在旧实现确实失败。
- 单次 Write 继承调用者 context，正 timeout 保留原秒数；零/负值使用 10 秒，溢出 duration 的正值拒绝。预算覆盖本次处理阶段与网络，不改变普通 PromQL 查询接口的配置行为。
- 已取消任务在转换/发送前退出；逐指标转换及序列化、压缩前后检查取消。没有将编码工作丢入后台 goroutine。单次 Protobuf 编码或 Snappy 压缩内部仍不能被 context 抢占，不能声称对任意大输入都严格在截止瞬间返回。
- HTTP 204 成功定义、Snappy/Protobuf 格式、样本/标签、请求级认证及自定义头保持；没有新增自动重试或修改写入目标。

## 验证

新增 6 个顶层用例，专项最终连续 10 轮通过：

1. 0、128、64 KiB、64 KiB+1 和 2 MiB 错误响应 fixture，读取数不超过 65,537，正文关闭；普通诊断保留，超限不回显正文。旧实现的超限/回显检查失败。
2. 响应读取异常 EOF 保留原因，旧实现丢弃该原因、检查失败。
3. transport fixture 验证默认 10 秒及已配 3 秒真实请求 context 截止；预取消和溢出配置在无客户端时也能提前结束。
4. 真实本地 HTTP：503 已返回头和部分正文后保持连接，调用者取消和已配 1 秒超时均使调用结束，并被服务端观察到；不只测试等待响应头阶段。
5. 真实本地 HTTP：解码收到的 Snappy/Protobuf，检查样本、标签、协议头、合成认证及附加头；204 写入正常，空集合仍不发送请求。
6. 标签转换期间发生取消，在网络访问前返回取消错误。

后端相关包非缓存回归、go vet 和 `go build ./...` 均通过。本地服务及合成凭据，不调用生产 Prometheus；没有生产吞吐/RSS/延迟结论。

## 发布与边界

只需后端新镜像；无配置格式/SQL/Redis/前端接口变更，无依赖升级。未部署生产。零/负数据源 timeout 的远程写入现在有 10 秒默认期限，之前依赖无限等待的部署需明确设置合适的正值，不能通过取消预算掩盖慢写入服务。

超时或取消无法撤销对端已接受的数据，结果可能不确定；不因此自动重试。本批仍一次编码整批指标，没有增加请求样本/字节截断，避免无声丢指标；超大写入批次的内存仍需要独立测量。成功 204 不额外读取正文，其他状态仍按原契约失败。

下一步继续处理即时拨测前端 POST 的取消与迟到响应隔离。真实 ICMP、Redis 迁移/执行取消、MySQL 执行计划、容器部署链路及生产容量仍未完成。
