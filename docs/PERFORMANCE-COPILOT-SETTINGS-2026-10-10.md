# Copilot 请求准备：配置复用与取消

日期：2026-10-10。后端基线 `e92cb29`；仅后端变更。

## 依据

流式消息、普通消息和诊断三个入口先调用 `Capabilities` 读取系统配置，再调用 `modelRuntimeConfig` 再读一次。对于正常成功准备，每个入口两次 `Setting.Get` 都查询同一条系统配置并解码 JSON。非管理员还需要成员、角色查询；这几处原来均没有继承请求 context。

## 改动

- 三个入口用 `agentRunSettings` 获取当前请求局部的配置和能力，只读取一次配置，再从已读取的模型配置构造内部请求。正常准备的系统配置查询次数从 **2 次变为 1 次**，不是整个请求 SQL 总数从 2 变 1。
- 配置、租户成员仓库增加 context 方法，旧无 context 方法保留兼容；角色 SQL 使用同一 context。
- 请求准备共用 10 秒阶段预算，继承调用者更早的取消/截止时间。流式、普通、诊断入口传入 HTTP 请求 context。
- 原 `Capabilities` 接口仍可用，内部使用独立的 10 秒预算；该无 context 接口的调用者不能继承 HTTP 断开，因此不能声称所有能力查询均已支持请求取消。
- 不跨请求缓存配置/角色/密钥，不把准备快照传给后续工具鉴权。每次工具调用和操作确认仍重新查询当前权限，既有确认/生产写入策略不变。
- 不修改模型环境变量回退、密钥解密和对外响应字段。配置在一次准备读取之后变化，将由下一次查询看到；不承诺多个独立数据表的读取形成数据库事务快照。

## 验证

专项连续 10 次通过：

- 三个完整服务入口连接本地 HTTP Agent fixture，每个只调用一次 context 配置读取；任何旧无 context 配置读取都导致测试失败。
- 测试密钥由现有加密函数生成，内部 HTTP 收到正确模型名和解密后测试值，不调用真实模型或外部 URL。
- 同一个服务下一次查询立即识别停用，验证没有跨请求缓存。
- 非管理员保留配置工具上限与角色权限交集，成员请求收到正确 tenant/user；取消后角色 SQL 继承 context，取消/配置失败不继续查询成员。
- 实际 SQLite 仓库覆盖初始化配置筛选、两个租户同一用户不同角色、缺失租户/成员以及旧方法兼容。
- 配置/成员读取在连接池满时按调用方 30ms 截止时间退出；这是等待取消测试，不是生产查询耗时测量。
- 后端相关包回归、静态检查、构建通过。

```powershell
go test ./internal/services ./internal/repo -run '^TestAgent(Run|Configuration)' -count=10 -timeout 90s
```

## 发布与后续

仅需后端镜像，无迁移、配置或依赖升级；前端、独立 Agent 未改，未进行生产部署、真实模型调用或新增浏览器验证。回滚恢复前镜像即可。

已确认查询次数减少，不宣称生产耗时/吞吐改善比例。工具审计保存及部分业务工具读取仍使用无请求 context 的旧接口，不能把本批当作整个工具生命周期取消完成；数据库真实执行中断、Redis v6 在途取消、生产容量和既有其他待办仍需继续。
