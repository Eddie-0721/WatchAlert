# 通知网络请求预算与取消修复

日期：2026-10-10。开发基线：后端 `60b1c5f`，分支 `codex/notification-io-budgets`。

## 本批范围

本批先修复通知发送的网络边界，不直接并行处理共享告警事件。前端及独立 Agent 无代码改动，没有表结构、配置字段或部署协议变更。

| 已确认问题 | 已实施修复 |
|---|---|
| 企业微信、钉钉、飞书未先检查 HTTP 状态；缺失错误码时默认值 0 可误报成功 | HTTP 必须为 200；JSON 必须包含对应整数 `code` / `errcode`，且为 0 |
| 通知成功或失败响应存在无上限读取 | WebHook、SREFlow、Slack、企业微信、钉钉、飞书统一最多读取 64 KiB + 1 字节用于判定超限，并关闭响应体 |
| 消费者停止时 HTTP 通知仍等到自身超时 | 消费者 → 普通通知/升级通知 → 发送器 → HTTP 传递取消信号；组、事件、路由处理前检查取消 |
| 页面测试通知没有传递请求取消 | 控制器传入 HTTP 请求 context，经服务层传到发送器；不更改请求/响应 JSON 契约 |
| SMTP 库发送没有完整 IO 超时 | 保留 MIME 编码；使用 30 秒总预算与 socket deadline，取消时关闭真实连接，覆盖连接、TLS、SMTP 握手、收件人、数据及应答阶段 |
| 发送失败只打印日志，处理函数仍返回成功 | 保留每个渠道的通知记录与失败日志；向上传递首个发送错误，不积累与洪峰规模成比例的错误数组 |
| 成功日志重复输出完整告警内容 | 改为 eventId、noticeId、渠道；原有数据库通知记录内容保留 |
| 单个 goroutine 创建后立即等待，没有增加并发 | 移除通知组中的无效 errgroup 包装 |

## 保持不变与兼容边界

- HTTP 仍使用已有连接复用方式与 10 秒请求超时；本批不改变历史 TLS 配置策略。
- WebHook/SREFlow 仍要求 HTTP 200，不擅自扩大为所有 2xx；Slack 仍要求 `ok`。
- 新限制会把超过 64 KiB、缺少必要错误码等异常应答标为失败，不再把未知结果记录成成功。外部系统可能已经接受消息，**不会因此自动重试**。
- 响应错误不再回显完整上游 body，避免日志扩张或泄露内容；保留 HTTP 状态和机器人业务错误码。
- 邮件仍使用 465 隐式 TLS，其他端口在服务端提供 STARTTLS 时使用它，保持证书校验。配置了认证但服务器不支持 AUTH 时明确失败，不静默跳过认证。
- 邮件 To/Cc/Bcc 信封及 MIME 内容保持；不向客户端返回完整邮件内容作为错误文本。
- SMTP 超时不等于外部未收到邮件，当前没有恰好一次投递保证，也没有新增自动重发。
- 30 秒是 SMTP 网络交换总上限；不是整个消费者批次或数据库查询的上限。
- `SendParams.RequestContext` 不参与 JSON 序列化；旧内部调用未传 context 时继续使用应用 context / Background 兼容。

## 本地验收

已通过：

1. 六类 HTTP 发送器的 Send/Test：500、429、超大成功/失败响应均报错，错误不回显上游内容。
2. 三类机器人应答：显式整数 0 成功；缺失、null、字符串、非零及非法 JSON 失败。
3. 六类 HTTP 发送器：等待响应头、读取响应体时取消均终止真实请求；原有连接复用回归仍通过。
4. 响应读取最多 65,537 字节，超限关闭响应体。
5. 模拟 SMTP：正常 MIME 和 To/Cc/Bcc 信封、无 Bcc 头泄露、卡住 greeting/reply 后取消、父级 deadline、隐式 TLS/STARTTLS 握手取消、拒绝不可信证书、配置认证不可静默跳过；隐式 TLS 与 STARTTLS 的完整认证投递均通过。
6. 已取消消费者通知/升级任务不访问 DB/Redis；页面测试通知取消能传到 HTTP 服务端。
7. 本批相关测试连续 10 次通过。
8. 后端测试：`go test ./cmd ./alert/... ./internal/... ./api/... ./pkg/client ./pkg/tools ./pkg/provider ./pkg/medium/... ./pkg/oidc -count=1 -timeout 120s`；二进制构建通过。

以上使用本地 HTTP/SMTP 模拟服务；没有发送真实短信、电话、邮件或 WebHook，没有访问生产，没有容器构建/生产压测结论。Windows 环境没有可用于 Go race 的 C 编译器，未宣称 race 检查通过。未运行包含固定私网外部服务配置的 `pkg/provider/test` 示例。

## 下一批与未解决问题

- 短信/电话适配器仍存在 Background 与旧 SDK 路径：须补端到端取消、响应预算、明确业务结果与重试策略；本批不声称全渠道已具备取消能力。
- 通知组仍顺序发送；慢渠道仍影响同组后续渠道，只是 HTTP/SMTP 等待现在有明确边界。后续先分离状态处理与不可变通知载荷，再引入有界队列/工作线程，避免共享事件指针竞争。
- 消费者重复 Submit 的生命周期、跨实例重复发送、完整事件写回覆盖认领/评估状态，仍需单独修复。
- `LastSendTime` 目前仍是尝试节流时间，不能作为送达证明；静默判断失败的策略、发送前时间戳写入、恢复事件先删除后落历史等可靠性问题仍未解决。
- 通知记录落库失败仍仅日志，尚无可靠 outbox。不能将本批称为“端到端可靠投递完成”。
- 系统目标仍包括规则恢复全中心扫描、其他 provider、长会话、前端大列表与代理缓存配置等，未缩减目标为本批改动。

## 发布与回滚

经上述本地验收后按既定约定合入后端 `eddie`；只需重新构建后端镜像，前端/Agent 无配套更新要求。代码推送不代表生产部署完成。

生产低风险验收应选现有测试通知对象，确认成功通知记录、失败错误码、邮件发送与停止任务后的连接释放；不要向实际值班组发送故障洪峰。异常时回滚到本批前的后端镜像（代码基线 `60b1c5f`），没有数据库迁移需要回退。
