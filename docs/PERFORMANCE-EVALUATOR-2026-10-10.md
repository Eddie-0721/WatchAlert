# 性能优化第三批：规则评估运行链路

基于后端 `7b37a30`，开发分支 `codex/performance-evaluator`。前端和独立 Agent 本批不变。

## 修复与可验证收益

| 热路径 | 原行为 | 本批行为 |
|---|---|---|
| Prometheus 评估 | 每轮先健康请求，再实际查询；健康检查新建客户端 | 直接执行真实查询，沿用 HTTP/结果完整性校验；每数据源每轮基础请求 2 → 1（不含用户配置的 callback 查询） |
| 查询并发 | 启动时的 10 并发只限制安装评估器，运行时按数据源数量创建 goroutine，无全局上限 | 告警/记录规则共享每进程查询槽，默认 32；每条告警规则最多 4 个工作协程；取消中的等待任务不会继续查询 |
| 记录规则数据源 | 查询前重复读取同一数据源两次 | 一次按租户读取，结果复用于查询；拒绝跨租户、停用和非 Prometheus 数据源 |
| 规则启用状态 | 每轮加载完整规则，按 ruleId 查询 | 仅查询 enabled，包含 tenantId，保留每轮实时检查，不缓存启用状态；查询失败/停用重置连续恢复标记 |
| Prometheus 阈值处理 | 每样本/每等级重复解析阈值、构建丢弃的事件；不触发时重复读取缓存 | 每轮每等级解析一次，已读缓存复用；没有待更新告警且阈值未越界时不构建事件。1000 样本×3等级测试中相关事件读取 6000 → 3000 |
| 恢复时间戳 | HGETALL 后又按事件逐个 HGET | 一轮只读取一次快照；读取/时间戳解析失败终止恢复，不能把失败当作没有待恢复记录 |
| 预告警匹配 | 每条事件线性查找当前指纹列表 | 构建集合后常数级查找 |
| 启动/重复提交 | 为所有规则额外创建启动 goroutine；相同规则重复 Submit 可遗留旧评估器 | 直接安装定时器，真正的并发控制放在运行阶段；Submit 取消旧 context，取消后 panic 不重启旧评估器 |

Prometheus 的运行取消传递到真实 HTTP 请求和 callback 查询；记录规则也用于 remote write。CloudWatch 指标查询和 Kubernetes 事件查询接收评估 context。告警推送在获取锁后及写入前再次检查取消，避免已停止请求继续产生副作用。该检查不是跨进程事务，不宣称解决所有并发状态竞争。

## 配置

现有配置不添加字段也可运行，默认值为：

```yaml
Evaluation:
  maxConcurrentQueries: 32
  maxDatasourcesPerRule: 4
```

范围分别为最多 256 和 32，非正值采用默认值。全局查询槽在进程首次使用时初始化，修改配置需要重启；多副本的总并发需要乘以实际执行评估的副本数。该上限保护数据库/上游和本进程，不能保证所有规模都在评估间隔内完成；慢查询在高负载时可能延迟下一次评估，需结合实际规模调参。原有“查询结束后等待下个间隔”的周期语义不变，不累积重放错过的 tick。

本批未改 SQL 表、Redis key、告警指纹或阈值规则。无需迁移已有数据，仅更新后端镜像；回滚使用前一镜像即可。

## 验证范围

- `go test ./alert/... ./internal/... ./api/... ./pkg/provider ./pkg/aws/cloudwatch -timeout 120s` 通过。
- `go test ./alert/eval -count=10 -timeout 90s` 通过，覆盖真实本地 HTTP 服务请求计数、12 个并行规则/96 个查询的限流与完整执行、单规则 fanout、在途与排队取消、记录规则租户隔离和重复读取、1000 样本/3等级缓存读取数、1000 个恢复时间戳只读一次。
- 保留并通过既有查询失败、超时、截断、部分数据源失败、worker panic、无条件规则、连续恢复等待窗等回归。
- SQLite 用例验证启用状态读取的租户边界、修改后即时可见和请求取消；关闭的 Redis 客户端验证恢复快照错误传播。
- 未使用生产数据、未调用真实云/Kubernetes 服务、未部署容器。当前本机 `CGO_ENABLED=0` 且无 GCC，未执行 Go race detector；重复并发用例不能替代 race detector。

## 尚未完成的引擎优化

1. 每规则恢复仍读取整个故障中心的事件哈希。需要完整的规则索引/冷启动及滚动升级方案，不能用 TTL 快照无声代替最新状态。
2. 日志/链路等非 Prometheus provider 的前置健康检查仍保留；需先审查它们的查询失败、HTTP 状态和空数据语义，才能安全移除。部分 provider 尚不支持即时取消；它们仍占用查询槽直到自身超时/返回，本批没有通过遗弃 goroutine 假装取消。
3. 全体规则启用查询仍可能同时访问 SQL；连接池、查询索引与数据库取消继续在后续批次处理。
4. 全站性能目标还包括通知慢通道、静态资源代理、长会话/大型列表以及基线验证，未因本批通过而宣布整体完成。
