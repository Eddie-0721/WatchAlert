# 通知并发前置：事件状态写入协调

日期：2026-10-10。基线：后端 `239e89c`；开发分支 `codex/event-state-coordination`。

## 证据与本批改动

原来评估、认领、普通通知和升级通知都调用 PushAlertEvent，直接 HSET 整份事件 JSON。调用方持有的旧副本可能覆盖其他操作刚更新的标签、认领人和时间戳。按规则聚合还会更新所有成员后，再更新一次代表事件。

本批按现有职责划分写入字段，不增加新业务状态：

| 写入方 | 现在的写入规则 |
|---|---|
| 普通通知 | 只更新 last_send_time，时间不得倒退；核对事件身份与状态，跳过已删除、已替换、已恢复的事件 |
| 升级通知 | 只更新 confirmTimeoutSendTime；最新记录已认领则不加入本次升级聚合；写入失败不假装已更新 |
| 认领 | 只修改认领字段，保留其他字段和首次认领者；并发第二次认领沿用原接口“已认领”的统计含义，不抢占归属 |
| 评估 | 更新监控字段时保留最新认领状态和通知时间；恢复仍按已有语义把普通通知时间重置为 0 |

- 使用原始 JSON 的读取—比较—写入（CAS），单 key Redis 脚本执行原子比较，不在 Lua 内重新编码 JSON。
- 本地 JSON 局部更新使用 RawMessage，保留未知字段、空数组和大整数值。评估输入中的监控标签仍按既有模型序列化，不宣称解决所有历史浮点精度问题。
- 竞争最多重试 4 次，持续竞争明确返回错误，不无限重试。更新时间未变化时可仅一次读取后返回。
- 身份包含租户、故障中心、指纹、规则、事件 ID、首次触发时间；评估兼容一次性填充旧缓存缺失的 ID/首次时间，但不允许替换已存在的身份。
- 拒绝评估时间倒退和已恢复事件回退；已删除的事件不能被待恢复/已恢复写入重新创建。
- 通知聚合仅在内存中组装内容，不再把聚合注释或 DutyUser 整份写回缓存；每个成员的通知时间最多更新一次，按实际处理该组的时间记录。
- 缓存更新失败向调用方返回；评估发布失败不再完全忽略，记录规则与指纹，便于定位。
- 恢复通知设置为空时按现有 FaultCenter 默认值“不发送”处理，避免空指针导致消费者重启。

## 性能与兼容性边界

这是安全增加通知并发的前置修复，**不是已经证明的吞吐提升**。有变化写入通常需要 HGET + CAS 两个 Redis 操作，首次脚本加载可能多一次；原来的裸 HSET 只需一个。最多 4 次竞争重试带来有界额外开销。下一步需要结合有界调度、事件索引及真实负载确认总收益，不能把并发安全测试当生产性能压测。

Redis JSON 格式与 key 不变，前端/Agent 没有配套协议变更，不增加数据库字段。部署必须允许 HGET/HSET/EVALSHA/EVAL；之前静默生命周期已使用脚本，本批评估与认领也依赖它。权限不足会明确失败，而不是降级为不安全全量覆盖。

混合运行旧后端仍可能裸写覆盖新字段，因此生产验证应确保全部后端副本更新；这不是只改一个副本就具备跨版本并发保障的方案。回滚可使用 `239e89c` 对应镜像，没有 DB 迁移，但回滚会恢复原有覆盖风险。

## 已验证

- miniredis：最新标签/评估时间/认领人保留；旧评估写入保留认领与通知时钟；重复/倒退通知时间不写入。
- 未知 JSON 字段、空数组、9007199254740993 等数值在局部更新时间/认领时不丢失。
- 删除、不同事件 ID、不同首次时间、错误租户、恢复状态、损坏 JSON 均不能被旧局部更新覆盖。
- 24 路并发认领保留首个认领者；24 路通知时间更新不丢认领；已认领事件拒绝升级更新时间。
- 在读取与写入之间注入并发修改，CAS 冲突后重新读取并保留新数据；持续冲突最多 4 次退出。
- 旧评估不能复活已恢复事件，恢复写入不能复活已删除事件，历史缺失身份可兼容填充且不会反复换 ID。
- 消费者普通/聚合通知每个成员只更新时间一次；时间更新失败/身份不匹配不进入发送；升级聚合必须以更新时间成功为前提。
- 恢复通知空配置、开启、关闭与非恢复状态用例通过。
- 缓存、消费者、认领服务、评估与静默相关测试连续 10 次通过；后端既定相关包非缓存测试及二进制构建通过。

没有连接生产 Redis/MySQL，没有真实通知或容器部署验收；当前 Windows 环境无 race 所需 C 工具链，未宣称 race 检查通过。

## 未完成与下一步

1. 恢复事件仍存在“删除缓存先于保存历史”的旧流程。需要先确定历史唯一身份、失败重试和数据库幂等约束；只交换两行会在 SQL 成功/缓存删除失败时引入重复历史。单独实施，不归为本批完成。
2. 时间戳仍表示尝试节流，不代表服务商受理或送达；多渠道失败的定向重试、幂等投递/持久队列尚未实现。
3. 多个消费者仍可能重复处理同一事件；本批没有分布式发送锁。认领在升级入组后、实际网络发送前发生的竞争窗口仍存在。
4. 评估之间同一秒的状态竞争、活动评估与用户删除的协调仍需进一步处理。本批保护的是认领/通知字段，不声称所有事件转换已线性化。
5. 静默读取失败仍可能按未静默继续，聚合也仍只按代表事件检查静默；后续必须在发送准备阶段修复，并避免改变静默数据的真实含义。
6. 有界发送调度、规则恢复全中心扫描、前端大列表/长会话、代理缓存及实际部署基线仍属整体目标，未缩减或完成目标。
