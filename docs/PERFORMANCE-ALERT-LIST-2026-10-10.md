# 告警列表：固定规模测量与扫描内存优化

## 范围与基线

后端基线 `9262c72`，分支 `codex/alert-query-performance`。前端、Agent、接口响应结构、静默规则语义与数据库结构不变。本批没有部署生产。

原流程为：读取各中心完整事件 → 复制全部结构体到切片 → 构建全部响应 → 全量排序 → 汇总 → 再复制队列切片 → 截取一页。采样确认大量分配/GC，以及 Label 别名查找反复遍历 map；不是根据文件名推测。

## 改动

1. 各中心逐个读取、逐条处理，不再积累第二份全量原始事件切片。
2. 使用最大堆保留排名前 `offset + size` 个候选；首屏 30 条最多保留 30 个响应候选。仍扫描所有事件，计算准确总数和筛选后、队列选择前的摘要；不把“找到一页”当作扫描完成。
3. 只排序保留候选，返回时复制所需页，避免小分页结果继续引用此前全部页的大结构体。深页保留数量会增加，并非所有请求都固定 30 条内存。
4. 队列和环境/服务摘要改为扫描时累计，仍保留原先恢复状态、预告警、认领、静默各自的优先级和统计范围。
5. 所有 Label key 均为无大写 ASCII 时使用直接查找，保留别名优先级；遇到混合大小写或 Unicode，仍执行原有 EqualFold 匹配。不改变 Agent 安全范围使用原始配置 Label 的规则。字符串值避免重复 fmt 格式化，非字符串仍按原逻辑转换。
6. 保留原排序主规则；不同故障中心中指纹相同且时间相同的行增加中心/数据源/事件 ID 排序键，修正此前未定义的随机顺序。新增分页乘法溢出检查，非法巨大页码返回错误，不触发越界或大容量预分配。

## 可复现的测量

环境：Windows amd64，Go 1.24.11，AMD Ryzen 7 7700，默认 GOMAXPROCS=16。两中心，共 1k/10k 告警；每中心 100 条精确匹配静默；每事件 20 个 Label；含已恢复、预告警和认领数据；请求第一页 30 条并带摘要。

### 预解码列表处理（排除 SQL、Redis 和 JSON 解码）

同一基准、1 秒/组、3 次、均启用 CPU profile；本地数据不是生产负载。

| 场景 | 优化前每次耗时 | 优化后每次耗时 | 优化前分配 | 优化后分配 |
|---|---:|---:|---:|---:|
| 1k / 全部 | 4.26–4.45 ms | 1.45–1.58 ms | 7.37 MB | 约 0.100 MB |
| 1k / 待处理 | 4.03–4.11 ms | 1.46–1.50 ms | 5.64 MB | 约 0.100 MB |
| 10k / 全部 | 53.58–54.88 ms | 21.01–22.40 ms | 107.80 MB | 约 0.100 MB |
| 10k / 待处理 | 49.82–50.98 ms | 22.27–23.77 ms | 81.24 MB | 约 0.100 MB |

独立无 profile 采样：预热 5 次、连续测量 100 次、排序取第 50/95 项：

| 告警数 | 优化前 p50 / p95 | 优化后 p50 / p95 |
|---|---:|---:|
| 1k | 4.515 / 5.519 ms | 1.505 / 2.509 ms |
| 10k | 53.182 / 58.200 ms | 20.069 / 24.082 ms |

这些是单请求列表计算的本地分布，不包括 HTTP/数据库/Redis/前端，不能表述为生产接口 p95。

### 实际缓存适配器 + 本地 miniredis

新增独立基准使用真实 go-redis 客户端、生产缓存 JSON 解码和上述列表逻辑；中心列表仍为 fixture，Redis 服务是 miniredis，不是真实生产 Redis：

| 告警数 | 当前链路耗时（3 次） | 整个测试进程每次分配 |
|---|---:|---:|
| 1k | 8.98–9.09 ms | 8.57–8.60 MB |
| 10k | 88.45–89.22 ms | 80.92–81.07 MB |

分配包含同进程 miniredis 的开销，不能直接当作后端进程 RSS。此层未测优化前对照，**不推算**整接口提升比例。它证明全量传输和解码仍是剩余成本，不将计算阶段约 100 KB 误报为整个请求内存。后续优先评估解码/传输及取消边界，不直接引入跨请求陈旧缓存。

## 回归证据

- 250 组固定种子过滤/分页组合，对比独立的原全量排序与汇总流程：默认/持续时间升降序、各队列、摘要开关、恢复开关、Label/认领/静默/Agent 范围、空数据、默认页和越界页；逐字段结果一致。
- 1,000 行候选测试确认堆大小上限；打乱输入 5 次仍得到稳定同指纹跨中心分页。大小写、Unicode case folding、空值、数字和数组 Label 保留原有格式行为。
- 实际缓存链路 1,000 行比对、每请求确认为 2 次事件 HGETALL + 2 次静默 HGETALL；后一个中心读取失败时即使第一页候选已满仍返回错误，不返回不完整成功结果。
- 新增关键测试连续 10 次通过；后端相关包回归、services vet 和构建通过。没有执行需要外部配置的 provider 示例测试，Windows 缺少 race 所需 C 工具链，未宣称 race 检测通过。

复跑：

```sh
go test ./internal/services -run '^$' -bench '^BenchmarkCurrentEventList$' -benchmem -benchtime=1s -count=3
go test ./internal/services -run '^$' -bench '^BenchmarkCurrentEventListRedis$' -benchmem -benchtime=1s -count=3
WATCHALERT_PERF_SAMPLES=1 go test ./internal/services -run '^TestCurrentEventLatencyDistribution$' -count=1 -v
```

PowerShell 的采样开关使用 `$env:WATCHALERT_PERF_SAMPLES='1'`，随后执行对应 go test。

## 发布与保留范围

本批只需更新后端镜像，无新增配置/表/索引，不依赖前端或 Agent 同时更新；沿用整体发布与回滚要求。未修改生产、未宣称容量验收完成。

剩余：当前事件 HGETALL/解码仍按中心全量执行；深页与全量导出仍有与数据量相关的内存/排序成本；纯正则静默、上千条静默、HTTP 并发、真实数据库及生产网络尚需扩展负载测试。列表请求取消尚未完整透传到缓存层。全系统目标继续，不能将本批通过视为所有性能问题完成。
