# 规则恢复扫描与指纹计算优化

日期：2026-10-10。后端基线 `ca46cd8`，开发分支 `codex/rule-event-index`。前端与独立 Agent 无修改。

## 实现

### 直接生效：消除重复双重循环

恢复判断原来调用 `GetSliceDifference`，对缓存指纹和本轮指纹做双重遍历。恢复函数已经持有本轮指纹集合，现在直接复用集合，每个缓存指纹只查一次。保留原顺序和重复项，不修改输入；全部仍活跃时不额外分配候选列表。

本机微基准（Windows/amd64，Ryzen 7 7700，Go 1.24.11，100ms × 3；两个列表相同、全部活跃）：

| 指纹数 | 原双重循环 | 新集合查询 |
|---|---:|---:|
| 1,000 | 0.935–0.956 ms/op | 0.00754–0.00759 ms/op |
| 10,000 | 92.0–95.4 ms/op | 0.0876–0.0950 ms/op |

这里只测候选筛选，复用恢复流程本来就创建的集合；不包含 Redis、JSON、监控查询与状态写回，**不能换算成系统整体加速倍数**。

### 分阶段启用：按规则读取事件

- 为每个事件源 Hash 新增派生 ZSET：`<原事件 key>:rule-index:v1`。成员为十六进制编码规则 ID、分隔符及指纹；不同规则的冒号、零字节、中文不会造成前缀混淆。
- 原事件 Hash/JSON/指纹保持不变。评估写入、认领、通知时间写入以及普通/恢复删除在原子脚本中维护索引。索引先于源写入更新；类型检查失败时不改源数据。
- 引擎恢复与按规则获取指纹改用 `GetRuleEvents`。开启后，Lua 原子读取成员与对应源值，只返回目标规则的完整事件，不缓存事件数据，也不缓存空结果。
- 每个进程首次读取某中心时，WATCH 源 Hash、完整读取、验证身份后，在事务中替换派生索引并写入完成标记。不会仅凭残留标记信任重启/回滚前的索引。
- 本进程同一中心的并发回填合并；最多 4 次事务竞争，失败后暂缓重建 1 秒，期间仍读取实时完整源数据。暂缓的是回填尝试，不是复用旧告警快照。
- 读取检查完成标记、索引成员数与源 Hash 字段数，以及选中成员对应值。缺失/部分索引重建；索引命令失败回退实时全量读取；源读取/JSON/身份验证失败明确返回错误，恢复流程停止本轮状态转换。
- 使用已有 Sonic 解码器，关闭索引时不引入另一种较慢的全量 JSON 解码路径。缓存入口复用同一实例，保存的仅是回填协调状态，不保存告警快照。

## 两阶段发布：默认不信任混合版本索引

第一阶段：所有后端更新到本批或更新版本，保留：

```yaml
Evaluation:
  ruleEventIndex: false
  maxConcurrentQueries: 32
  maxDatasourcesPerRule: 4
```

此时集合计算优化生效；新节点维护索引，但读取仍走实时全量路径。不要把“代码已合入”写成“生产扫描已减少”。

第二阶段：确认所有事件写入节点都已升级（包括非 Leader 上的认领/删除接口），再将 `ruleEventIndex` 设为 `true` 并重启后端。首读回填完成后才使用索引。未在页面增加配置项，也未在本轮操作生产配置。

即使索引读取关闭，新版写入仍需要索引维护权限：除原 HGET/HSET/HDEL/EVALSHA/EVAL 外，还需 TYPE、ZADD、ZREM；开启读取/回填另需 ZSCORE、ZCARD、ZRANGEBYLEX、HLEN、HGETALL、WATCH/UNWATCH/MULTI/EXEC、DEL，以及派生 key 的访问权限。按实际 Redis ACL/版本验收，不应只放行顶层 EVAL 命令。

当前项目使用单节点 `redis.Client`，本批多 key 脚本未增加 Redis Cluster 支持；不能假定不同 key 跨槽可用。

## 回滚、资源与完整性边界

- 回滚旧写入版本前，先在仍使用索引读取的所有节点关闭开关并重启，确保没有新读者依赖旧写者不会维护的索引。
- 再次开启时先完成全量升级和重启回填。无需删除原事件数据，也不需要改 SQL 表；上一批归档凭证表要求仍然有效。
- 索引占用额外 Redis 内存，每个事件一条成员，写入多一次 ZADD/ZREM 及类型检查；需结合真实数据评估内存、脚本耗时与回填开销。
- 冷回填仍是中心全量读取，繁忙中心可能连续 WATCH 冲突，此时安全回退但没有热索引收益；错误日志可识别回填失败。空中心会保留一个完成标记。
- 完整性计数不能检测人为修改索引但保持成员总数相同的所有情况。因此开启条件是所有正常写者都维护索引，不支持其他脚本绕过接口修改源/派生 key。测试覆盖重启后重建此类残留数据，但不宣称运行中可识别任意外部篡改。
- 单条规则本身特别大时，仍需返回该规则全部事件，Lua 执行及返回大小没有被伪装为固定常数。本批没有改变监控结果预算或丢弃超过数量的事件。
- 默认全量回退现在遇到损坏/跨作用域记录会报错，而不是跳过后继续恢复；必须核查错误记录，不能把损坏源数据当作正常空列表。

## 验证

- 1,001 条源事件中目标规则 50 条：冷回填读取完整数据，热查询仅一次 EVALSHA，响应为 50 对指纹/原始 JSON 加状态标记（101 个值），没有 HGETALL。
- 新事件、认领、通知时钟更新、普通删除和恢复 CAS 删除后，索引读取与源一致；删除到空只留下完成标记。
- 索引缺失、成员缺失、旧写者增加成员导致计数不符、重启后的同数量错误映射、24 个并发首读、任意规则前缀、Redis 故障、损坏源数据、取消与租户错配均覆盖。
- 在每次 EXEC 前修改源数据，四次 WATCH 竞争后回退到最新源快照，不写完成状态；紧接的请求暂缓重建但仍读取当前事件。
- 索引错误类型导致写入失败时，原事件 JSON 保持不变。恢复引擎读取失败不更改事件、不继续读取恢复时间戳。
- 缓存/评估/配置回归连续 10 次通过；配置样例 YAML 和开关反序列化验证通过。config、cmd、alert、internal、api、client、tools、provider、medium、oidc 相关包非缓存回归、相关包 `go vet` 以及后端二进制构建通过；未运行包含固定外部目标的 provider/test 示例包。
- 没有真实 Redis 压测、生产开关验收、容器部署或 Go race 检测结论。未宣称生产已启用索引或整体性能优化完成。
