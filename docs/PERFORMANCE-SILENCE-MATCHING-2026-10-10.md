# 静默匹配批量候选索引

日期：2026-10-10。后端基线：`7cbdd4e`。本批只修改后端，前端和独立 Agent 不需要更新。

## 发现与实现

原快照已避免重复读取 Redis 和重复编译正则，但对每条告警仍逐一尝试每条静默规则。对于 E 个事件和 S 条规则，未提前命中时有 E×S 次规则尝试。

本批增加请求内的**内存候选索引**，不是 Redis 持久化索引，也不需要开启此前的 `ruleEventIndex` 配置：

1. 所有生效规则仍先完整编译和校验；任意生效规则无效仍返回错误，不能被候选筛选隐藏。
2. 对包含 `=` 或 `==` 的规则选择一个必要条件作为索引键。在多个等值条件中，选择在本次规则集合中出现次数较少的 key/value，避免所有规则先按相同的 `env=prod` 聚到一起。
3. 候选筛选后仍执行原有完整 AND 条件；跨规则维持 OR 语义。不能仅因等值条件命中就认定静默。
4. 纯正则、否定条件继续使用原匹配器；不推断正则前缀，不把缺失、数字、nil、大小写不同的 Label 当作匹配。
5. 索引仅活在当前快照中，不跨请求缓存；不会延迟规则修改、生效或到期状态的重新读取。

`CompileBatchSnapshotChecked` 用于当前告警列表扫描，预计事件数至少 32 且规则数超过 8 才考虑索引；实际生效规则不足时仍使用线性路径。事件数只是性能策略提示，不是返回上限，也不影响业务结果。遍历候选时在索引 key 和事件 Label key 中选择较小集合。

原 `CompileSnapshotChecked`/`LoadSnapshot`/通知路径保留线性匹配，不承担批量索引的额外准备成本。两种入口复用同一生效时间和规则校验逻辑。

## 测量与代价

Windows / Go 1.24.11 / Ryzen 7 7700。告警列表使用固定预解码 fixture，每中心 100 条静默、两个中心，默认 30 条一页；包含完整过滤、摘要、队列与分页。3 次、每次 1 秒。

|场景|修改前|修改后|
|---|---:|---:|
|1k 事件，all 队列|1.46–1.48 ms|0.818–0.837 ms|
|10k 事件，all 队列|19.08–19.38 ms|12.50–13.30 ms|
|10k 事件，attention 队列|18.84–19.13 ms|11.94–12.97 ms|
|每次列表计算分配|约 100 KB / 669 次|约 159 KB / 915 次|

这是以约 59 KB 临时分配换取该固定场景约三分之一的计算耗时下降，**不是生产接口延迟或整体系统提速比例**。原始缓存仍全量读取/解码，网络和 JSON 成本未被消除。

包含真实 go-redis 客户端、生产解码适配器和同进程 miniredis 的现状测量：独立重跑 3 次、每次 2 秒，1k 为 7.22–7.43 ms/5.42–5.46 MB，10k 为 73.15–75.36 ms/49.69–49.75 MB。此前与本地检查交叠的一轮 10k 波动达 76–130 ms，故不据此推算稳定的端到端改善比例。上述 MB 包含模拟 Redis 的分配，不是后端 RSS；实际生产 Redis/SQL 未压测。

独立 matcher 微基准使用相同旧线性实现作为对照、已编译快照、未命中 Label（明确是旧实现最不利的全扫场景）：

- 100 条等值规则：约 1,600 ns→43 ns/次。
- 1,000 条等值规则：约 16,000 ns→44 ns/次。
- 100 条、10% 纯正则的混合规则：约 1,600 ns→150 ns/次。
- 纯正则仍线性扫描，未声称改善；两种匹配每次均无新增堆分配。

建立索引并非免费：100 条双条件规则的准备约 30 μs、49 KB，旧线性约 10 μs、20 KB；1,000 条约 349 μs、636 KB，对照约 93 μs、194 KB。通知路径仍约 9.5 μs/20 KB 和 94–98 μs/194 KB，不改为默认索引。规则总是很早命中、等值条件区分度低、少量事件或主要为正则的场景收益更小，甚至不能摊销索引成本；不会承诺每种分布都更快。

## 验证

- 独立旧逻辑对照：300 组固定种子规则、四个时间边界、随机缺失/数字/nil/字符串 Label。
- 正向命中、所有等值操作符、纯正则/否定回退、Unicode/大小写、重复 key 矛盾条件、无效生效规则不被隐藏。
- 1,000 条规则候选计数：未命中时不执行完整规则；命中服务但环境不匹配仍拒绝；命中完整规则只执行对应候选。
- 0/1/8/9/100 条规则与 0/31/32 等批量提示值对照，证明策略阈值不会改变结果；多 key、输入修改后的快照稳定性及并发只读复用。
- 静默、消费者、模型和事件服务回归连续 10 次通过；后端相关包完整回归、相关 go vet 和构建通过。既有列表 250 组参考对照及真实缓存适配器 + miniredis 测试仍通过，Redis 读取次数不增加。
- 无 UI 变更，本批没有重跑浏览器。未发送真实通知、未压测生产；当前 Windows 无 CGO race 环境，普通并发测试不能替代 race detector。

## 发布、回滚与剩余项

合入后端 `eddie` 后只需要重建后端镜像。无数据库迁移、接口字段、Redis 格式、配置或权限变化；可回滚上一版后端。未部署生产。
