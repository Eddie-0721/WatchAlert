# 通知准备与静默快照修复

日期：2026-10-10。后端基线 `2ae87e1`，分支 `codex/notification-silence-safety`。前端及独立 Agent 本批无修改。

## 已确认的问题和修复

1. 普通聚合通知原先只检查代表事件是否静默，其余成员可能被错误计入；第一条被静默也可能让整组非静默事件无法通知。现在每个源事件先匹配静默，再生成聚合内容，数量只包含实际可发送成员。
2. 静默读取失败原先等同于“不静默”，无效匹配条件被忽略。现在准备阶段返回错误并停止该组该路由发送，不更新时间；告警列表也返回查询失败，不伪装成未静默。旧布尔判断入口保守返回禁止发送并记录错误。
3. 普通通知时间原先在静默与路由检查之前写入；升级通知更早在候选收集时写入。现在仅在路由匹配、恢复通知配置允许、静默检查通过后执行局部 CAS 更新时间；未找到事件、状态变化或更新失败的成员不发送。
4. 升级通知原先截取第一条，其他等级的候选可能无法走正确路由。现在保留所有候选，按等级选择路由，再聚合该等级的有效成员。
5. 聚合注释及值班人只修改局部通知副本；收件人切片复制后再添加值班用户，避免意外改变配置或源事件。

## 性能与行为边界

- 每个“事件组 × 匹配路由”的准备过程只读取一次静默规则并编译一次，然后匹配所有成员。升级候选收集不再每条读取静默；单等级、单路由、1,000 个候选由逐事件检查降为一次快照读取（时间戳仍逐事件校验）。
- 不跨外部发送复用快照：前一路由返回后，下一路由重新读取，能够发现发送期间新增的静默。多路由场景因此比以前代表事件一次检查有更多读取；这是时效性保障，不声称所有场景 Redis 操作都下降。
- 本地时钟更新仍是**发送尝试节流**，不代表渠道成功。不同路由可能再次更新同一成员时间；失败通知仍遵循现有重试间隔，未引入自动重发未知结果。
- 快照读取、事件校验与真正发送之间并非原子事务；已经开始的外部发送无法被新静默撤回。没有宣称严格实时的跨系统一致性。
- 静默规则状态和起止边界保持原有定义；仅状态 1 且开始时间已到、结束时间未到生效。状态 0 仍依靠生命周期任务转为进行中。
- 无效的活动静默规则会阻止所在中心本次通知准备，并使相关告警查询失败；必须修复规则/缓存，不能静默忽略。该策略避免绕过静默，但也可能延迟本应发送的通知，需要关注后端错误日志。
- 本批没有修复恢复事件删除早于历史落库/发送的问题。因此恢复通知在静默读取失败时仍可能丢失，不能将本批等同于可靠投递完成。

## 验证

- 消费者、静默、事件服务测试连续 10 次通过。
- 本地 HTTP 模拟渠道覆盖聚合与非聚合、首个/非首个静默成员、无效活动规则、缓存失败、状态更新时间失败、无匹配路由、恢复通知关闭、取消与跨租户输入。
- 双路由测试在第一次发送期间加入静默：只发送一次，但读取两次静默；升级 P0/P1 分组保持正确等级和聚合数，源注释不被修改。
- 1,000 次内存标签匹配只读取一次静默快照；活动无效正则报错，未来或已过期无效规则不干扰当前准备。
- 后端 cmd、alert、internal、api、client、tools、provider、medium、oidc 相关包非缓存测试通过。未运行带固定外部目标的 provider/test 示例包。
- 后端二进制构建通过；产物在本机临时目录，未部署。
- 无真实渠道消息、生产访问、负载压测、容器构建或竞态检测结论；当前环境未具备 Go race 所需 C 工具链。前端/Agent 未改，不宣称本批验证了浏览器或模型。

## 发布与后续

只需构建新的后端镜像；接口、Redis 格式、数据库字段及配置未变，保留上批 Redis 脚本权限要求。回滚可用 `2ae87e1` 镜像，但会恢复本页描述的静默/聚合问题。代码合并与推送不等于生产已部署。

整体性能目标仍未完成：有界通知调度、消费者生命周期、恢复历史幂等保存、规则维度缓存索引、长会话分页、部署代理及生产数据库索引验证继续在待办中。
