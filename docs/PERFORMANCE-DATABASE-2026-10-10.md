# 数据库性能优化记录（2026-10-10）

基于后端 `6b963b1`，开发分支 `codex/performance-database`。本批不修改前端、Agent、表结构或生产数据。

## 已实施

| 路径 | 原问题 | 本批处理 |
|---|---|---|
| SQL 连接池 | 未显式限制最大连接数 | MySQL 每进程默认最多 32 个连接、8 个空闲连接；连接最长 30 分钟，空闲最长 5 分钟；可配置。SQLite 保留 1 个连接，避免并发写入争用和内存数据库被连接回收清空 |
| 故障中心 7 天 MTTR/MTTA | 读取最多 999,999 条历史完整记录（含标签/正文），再多次遍历；查询未按时间过滤 | 一条聚合 SELECT 返回 28 个标量，转换成原有两组 7 天数组。日期仍按服务端本地午夜，MTTR 按恢复日、MTTA 按认领日，允许认领与恢复跨日；不用恢复时间单独过滤掉有效认领 |
| 历史告警/通知记录 | 缺少页大小上限、取消传递 | 传递 HTTP context，服务层上限 30 秒，校验分页和偏移溢出；通知每页最多 100 条。历史接口保留现有 HTML 导出的 10,000 条上限，不把旧导出功能意外限制为 100 条 |
| 评估器数据源读取 | SQL 查询不随规则停止取消 | 告警、记录规则及 Kubernetes 配置查询使用可取消、按租户隔离的数据源读取 |
| 索引维护 | 热路径缺少统一的索引核对/实施入口；历史 TEXT 字段不适合直接添加普通索引标签 | 增加只读计划工具，按实际字段类型生成待审核 SQL。不自动创建索引，不缩窄字段，不调用启动迁移或重写权限记录 |

30 秒取消是请求侧预算，数据库驱动/服务端终止执行的实际时延仍需线上核验。连接上限并非性能承诺：多副本总连接、现有其他客户端以及 MySQL `max_connections` 需要一起评估。

## 配置与兼容

旧配置可直接运行；如需调节 MySQL，在已有 Database 段添加以下可选项，不要创建重复段：

```yaml
Database:
  # 保留现有 type/host/port/user/pass/dbName/timeout
  maxOpenConns: 32
  maxIdleConns: 8
  connMaxLifetimeSeconds: 1800
  connMaxIdleTimeSeconds: 300
```

非正数中 0 表示 open/lifetime/idleTime 使用默认值；idle 明确配置 0 表示不保留空闲连接。负数拒绝启动。最大连接数不超过 4096，生命周期配置不超过 7 天；idle 大于 open 时收敛到 open。SQLite 应省略这些 MySQL 配置；显式设置与单连接保留模式冲突时返回错误。

HTTP 成功响应结构不变。历史超过 10,000、通知超过 100 的单次请求现在明确返回参数错误，而非无界读取。既有前端历史导出仍可用，但大型 HTML 导出仍占浏览器内存，分批导出留待后续。

## 索引计划：独立审核，不随更新自动执行

在后端根目录使用已有安全配置运行：

```sh
go run ./cmd/performance-indexes > performance-index-plan.sql
```

工具仅读取数据库元数据并输出 SQL；SQLite 文件必须已存在。不要直接将输出管道接入数据库客户端。输出包含规则启用查询、历史列表、通知趋势/列表/过期删除、Agent 最近消息/会话以及审计列表的候选索引。

上线前逐项确认：

1. 当前数据库版本、实际表引擎、数据量、字段类型和已有等价索引。同名索引会输出核验提示，不能只凭名称认定列定义正确；不同名等价索引需人工去重。
2. 真实查询的 EXPLAIN、磁盘空间和业务低峰窗口。MySQL 历史 TEXT/长字符串采用前 64 字符索引，可能存在前缀碰撞和额外排序，不能套用 SQLite 的计划结论。
3. MySQL SQL 明确要求 `ALGORITHM=INPLACE, LOCK=NONE`，不支持时应停止并评估，不自动退回阻塞建表方式。即使支持在线索引也可能短暂等待元数据锁并增加 CPU/I/O。
4. 执行后再次 EXPLAIN、观察连接等待/慢查询/写入延迟，并记录真正安装的索引。本次没有连接生产库、应用索引或运行生产 EXPLAIN。

服务更新不依赖这些索引已经安装；代码回滚不需要回滚数据库结构。若后续安装了索引，回滚服务时也不必立即删索引，索引变更另行审核。

## 本地验证

- 后端 `go test ./alert/... ./internal/... ./api/... ./pkg/client -count=1 -timeout 120s` 通过。
- SLO 使用 1,004 条合成历史、跨租户/故障中心和跨日期数据，比对原 Go 统计口径，确认仅一次 SELECT；取消请求返回错误。
- 历史/通知分页、搜索的租户范围、过大请求拒绝、现有 10,000 条导出参数兼容和数据源 SQL 取消均有回归。
- SQLite 池上限、等待可取消、20 个并发插入、内存数据库保留，以及独立 OpenDB 不创建表均有测试。
- 索引工具测试证实计划阶段不建索引；仅在隔离 SQLite 中应用 SQL，EXPLAIN 检查规则/历史/通知/Agent 查询使用候选索引。不是 MySQL 实测。

未连接真实 MySQL、未部署容器、未测生产 p95/容量、未执行 race detector。本批无前端代码变化，没有宣称完成浏览器或生产联调。

## 保留的边界与后续工作

- MTTA 仍从 JSON 提取认领时间，OR 时间条件可能扫描该租户/中心较多历史行。改为聚合减少传输和 Go 堆分配，不等于数据库扫描量已被消除；独立认领时间列及迁移需要单独评估。
- 正常类型数据的统计口径已回归；历史异常 JSON/非整数认领时间的数据清理未实施。无效 JSON 可能使统计失败，不能当作零值健康结果。
- LIKE 模糊搜索、深 offset 和 COUNT 总数仍有成本；没有把所有页面改为游标分页。
- 仍待处理：规则恢复全中心 Redis 扫描、非 Prometheus 上游连接和错误语义、通知慢通道、长会话加载与静态资源代理。全系统目标尚未完成。
