# WatchAlert 三仓库系统性审计报告

审计日期：2026-10-08

性质：只读审计；唯一新增交付物为本报告。未修改业务代码、删除文件、升级依赖、提交或推送。

目标：统一工程规范和交互体验，优先保障告警可信、操作真实生效、权限不越界；不以重构或换框架为目标。

## 1. 结论摘要

当前 Go 后端、React 前端、Python Agent 的分工可以继续使用，不需要整体重写，也暂不需要增加微服务、消息平台、全局状态框架或新的 UI 组件库。

当前主要问题不是视觉风格，而是不同迭代之间的契约与行为没有完全统一：

1. **安全应先于扩展 AI**：缺失租户头可绕过权限中间件；部分数据源读取未限定租户；审计日志直接保存原始请求体，可能记录模型及其他凭据。
2. **告警和操作结果必须可信**：查询失败可能进入告警恢复流程；静默数据库状态与 Redis 生效状态可能不一致；认领和 Agent 操作存在“返回成功但实际未完成”的路径。
3. **Agent 已独立，但三仓库未完全对齐**：新 Agent 定义的 7 个 Prometheus 工具尚无对应后端 Gateway 实现；单条告警工具没有真正按指纹定位；证据校验仍可接受失败证据。
4. **UI 基础已经具备，应修流程而非再换皮肤**：现有主题、页面容器、路由懒加载、新告警工作台、静默预览和浏览器测试值得保留。优先修筛选状态丢失、错误伪装为空数据、中间断点信息消失和窄屏规则维护不可用。

本报告列出 **26 项问题：P0 3 项、P1 14 项、P2 9 项**，另列需要运行数据验证的风险。P0/P1 的优先级针对影响，并不表示已经在生产环境发生事故。没有访问生产数据，也没有实施生产漏洞利用。

## 3. 优先级与工作量说明

## 4. P0：先处理安全边界

### SEC-01 缺失租户头绕过权限检查，系统设置存在凭据暴露路径

- **范围/证据**：后端 [Permission.go:16](C:/Project/WatchAlert/internal/middleware/Permission.go:16) 对空或字面 `null` TenantID 直接 `return`，但不 `Abort`；Gin 仍执行后续处理器。系统设置路由 [settings.go:26](C:/Project/WatchAlert/api/settings.go:26) 没有 ParseTenant，Get 只清除 Agent 模型密钥字段，[services/settings.go:85](C:/Project/WatchAlert/internal/services/settings.go:85) 仍返回其他设置模型；模型中存在邮件 token、LDAP 密码、OIDC clientSecret 等可序列化字段。
- **确认程度**：中间件绕过已用隔离路由复现；设置读取链路代码确认，未读取生产凭据。前提是调用者已登录、相关配置确实存在。
- **影响**：无对应权限的登录用户可能读取全局敏感配置；`syncLdapUser` 同样进入该路由组。全局设置本身也不应仅用普通租户权限表达管理权。
- **最小修复**：租户业务请求 fail-closed；全局系统设置显式校验平台管理员。设置读取返回脱敏 DTO，用 `xxxSet` 表示已配置；保存空密钥表示不修改，清除应为显式操作。
- **验收**：空、`null`、不存在、非成员租户及普通用户均不能越权；任意读取响应不含密钥原文或密文。
- **工作量/依赖**：后端 1–2 人日，前端设置页约 0.5–1 人日；后端主导、前端适配只读 DTO。

### SEC-02 数据源 ID 查询没有统一租户限定

- **范围/证据**：[services/datasource.go:115](C:/Project/WatchAlert/internal/services/datasource.go:115) 忽略请求 TenantId，调用仅按 ID 查询的 [repo/datasource.go:64](C:/Project/WatchAlert/internal/repo/datasource.go:64)，直接返回含 Auth、KubeConfig 等字段的模型。日志预览 [api/datasource.go:260](C:/Project/WatchAlert/api/datasource.go:260) 也复用该读取；`/c/getJaegerService` 路由没有 Permission 中间件。已有 `GetForTenant` 仅被部分新接口采用。

- **最小修复**：所有用户可达资源查询携带可信租户 ID；复用已有 `GetForTenant`，区分“内部评估器读取完整连接”和“页面读取脱敏连接”。审查 ID 查询、更新、删除链路，不只补一个控制器。

## 5. P1：告警、操作、Agent 与关键交互可靠性

### REL-01 评估失败可能误恢复；多数据源指纹还存在碰撞条件

- **证据**：[alert_rule.go:144](C:/Project/WatchAlert/alert/eval/alert_rule.go:144) 将各数据源指纹合并后无条件执行 Recover；数据源不健康或查询失败返回 nil，[query.go:31](C:/Project/WatchAlert/alert/eval/query.go:31) 与“成功但无触发”没有可区分结果。Recover 将缺失指纹转为待恢复，超过等待期转为已恢复，[alert_rule.go:296](C:/Project/WatchAlert/alert/eval/alert_rule.go:296)。同文件 query.go 中指纹依据指标标签、规则 ID/名称、级别生成，数据源 ID 未纳入，外部环境标签在指纹生成后才合并。
- **影响/确认**：代码确认。数据源持续失败可能导致假恢复；同一规则跨数据源、指标标签相同时可能覆盖同一故障中心中的事件。未在真实 Redis/Prometheus 故障环境复现。
- **建议**：返回带 `datasourceId/status/error/fingerprints/truncated` 的评估结果；只允许成功且完整的对应数据源结果驱动恢复，失败显示“评估异常/状态未知”。将数据源维度纳入事件身份，制定旧指纹过渡策略，不能直接改哈希造成所有告警重建。截断查询结果同样不能据此判定其余事件恢复。
- **验收**：模拟超时、健康检查失败、部分数据源失败和截断结果，既有活跃告警不误恢复；相同标签的两个数据源保持独立事件；正常恢复仍有效。
- **工作量/依赖**：3–5 人日；后端，前端需要显示评估异常；指纹变更需兼顾历史、静默上下文和 Agent。

### REL-02 请求解析失败未终止服务执行，异常 token 可触发 panic

- **证据**：[api/entry.go:22](C:/Project/WatchAlert/api/entry.go:22) 的 BindJson/BindQuery 不返回错误，控制器调用后继续 Service。隔离测试构造非法整数字段，服务仍执行，HTTP400 响应拼接了失败与成功两个 JSON。[Auth.go:58](C:/Project/WatchAlert/internal/middleware/Auth.go:58) 未验证长度即切片 Bearer token，短输入已复现 panic。
- **影响/确认**：已复现。错误请求可能发生业务副作用，响应不再是合法单一 JSON；无效身份输入变成服务器错误而非认证失败。
- **建议**：绑定函数返回 error/bool，控制器立即返回；Service 防止已中止上下文继续执行作为过渡防线。身份头先解析 scheme 和长度，不依赖 recover。
- **验收**：非法 JSON、字段类型、query 和短 token 返回一次稳定错误；服务副作用计数为零。

### 8.1 API 与数据边界（SEC-01/02、REL-02、AI-01/04、ENG-03）

### 9.3 四条核心流程的最小改造

1. **定位与认领**：保持环境/服务筛选 → 展示原始事件 → 认领返回逐项结果 → 刷新当前事件，不用前端乐观状态掩盖失败。
2. **创建静默**：从真实Label构造条件 → 选择资源/服务范围 → 后端预览 → 明确时长与影响 → 提交 → 展示保存及生效状态 → 返回原查询。现有预览能力应保留。
3. **规则维护**：Manage为统一检索入口 → 规则页显示启用与评估分别的状态 → 测试/预览 → 保存 → 检查最近评估。模板是创建起点，规则组是组织结构，不默认引入模板自动同步/继承平台。
4. **AI辅助**：携带告警ID和租户上下文 → 精确读取与授权取证 → 提供带证据的假设 → 写操作生成提案 → 用户确认且后端再次校验 → 核对实际状态。Agent无权限时解释原因，不提供绕过路径。

## 10. 分阶段实施计划与验收

### 阶段A：安全与告警真实性止血

范围：SEC-01/02/03、REL-01/02/03/04，以及ENG-01中阻断测试的基础问题。

- 可先独立处理：token解析、绑定失败立即返回、日志格式vet修复、静默删除从真实对象取缓存键。
- 需要前后端协作：凭据只读DTO、逐项操作结果、静默生效反馈、评估异常显示。
- 不做：换框架、修改整站视觉、增加AI工具权限。
- 验收门槛：双租户隔离、合成密钥不泄漏、非法请求无副作用、失败查询不触发假恢复、缓存故障不报假成功、重复确认不重复执行。
- 建议先拆为小PR/小发布；涉及指纹的修改单独评估兼容与回滚，不能混在样式发布中。

### 阶段B：完成三仓库Agent契约与日常核心体验

范围：AI-01至AI-06、UI-01/02/03、必要的scope语义修复。

- 前端可直接修：筛选分页一致、页面错误态、中间断点状态、窄屏规则组切换、证据编号展示（后端字段同步）。
- 跨仓库配合：工具清单/权限/数据范围、告警精确读取、证据验证、流式最终状态、取消和超时。
- 验收门槛：真实Gateway契约通过；所选告警不串事件；失败证据不支持确定结论；未授权工具不可调用；四条核心流程在390/700/1440px通过，包含500/403/超时/重复确认。

### 阶段C：收敛工程与信息架构，按测量结果优化性能

范围：P2项中已确认收益高的内容，包括规则真实评估信息、共享告警组件、发布文档、有限上下文、重复Redis读取和大块依赖。

- 先测量再决定：数据库索引、全量告警索引化、虚拟列表、大规模上下文总结。
- 验收门槛：全新克隆可按文档部署指定三版本；旧目录引用迁移可追溯；同对象跨入口状态一致；构建/查询/模型预算有基线与对比数据。
- 暂缓：完整Incident管理平台、自动根因归并、全仓TypeScript迁移、全量表单重写、任意外部系统连接器市场、多Agent自治写入。

## 11. 后端/Agent需要的最小契约调整

| 契约 | 建议内容 | 是否立即需要 |
|---|---|---|
| 安全设置/数据源读取 | 安全DTO、credentialSet、明确清除动作、平台/租户权限区分 | 阶段A |
| 告警精确获取 | tenant + event fingerprint + 合法scope，not_found不退化列表 | 阶段B，AI分析前置 |
| 评估结果 | datasourceId、最近评估时间、success/error/unknown、错误摘要、完整性标记 | 阶段A内部先做，阶段C页面完善 |
| 静默与认领结果 | saved/effective或同步错误、逐项结果、可核对对象ID | 阶段A |
| 工具能力与契约 | 真实支持的工具、权限交集、schema/version、缺失能力原因 | 阶段B；可扩展现有capabilities，不必新增一套服务 |
| Evidence | evidenceId、tool、status、时间范围、对象/数据源、脱敏摘要、truncated、safeError | 阶段B |
| AI执行限制 | runId、deadline、取消传播、统一工具预算、用户并发、大小限制 | 阶段B |
| 统一scope | environment/service/cluster/namespace/resource/owner及来源Label；未知明确为空 | 阶段B/C |
| 历史筛选/规则健康 | 可查询环境/服务、最近评估与触发数据，历史缺失有兼容策略 | 阶段C，先修前端不实文案 |

不建议为了字段规范立即进行破坏性全库迁移；优先通过DTO和兼容层统一读取语义，必要的数据迁移单独设计。

## 12. 建议的下一步决策

建议批准阶段A，先修后端安全与告警真实性，再并行修前端筛选/失败态。Agent先收敛到实际可用工具，并修正精确定位及证据护栏，再扩展外部系统能力。

本阶段没有删除旧Agent、没有改变分支、没有改生产配置，也没有把测试通过解释成全系统安全或性能达标。后续每项实现应引用本报告问题编号，并附针对性验收结果，避免再次以“页面看起来正常”替代业务正确性。
