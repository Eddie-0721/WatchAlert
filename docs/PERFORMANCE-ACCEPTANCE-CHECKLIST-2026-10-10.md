## 3. Redis 候选与生产构建分支的同机对照

使用未修改的 `BenchmarkCurrentEventListRedis`。基准调用实际 `cache.NewEntryCache → client.InitRedis`，因此分别使用两个版本的生产客户端配置，不是随意构建默认客户端；事件/静默/中心 fixture 完全相同。两个中心、每中心 100 静默规则，第一页 30 条且含汇总。服务端为同进程 miniredis，中心列表为 fixture，不是真实 Redis 或 SQL。

先分别运行三次 `-benchtime=1s`：

| 事件数 | v6 / eddie ns/op 换算 ms | v9 候选 ms |
|---|---|---|
| 1,000 | 7.302 / 7.359 / 7.271 | 8.097 / 8.122 / 7.966 |
| 10,000 | 75.597 / 76.274 / 75.754 | 81.415 / 85.776 / 83.915 |

第一组候选较慢，因此继续反向顺序采样，而不是直接声称升级提升性能。固定各版本编译产物，再做 v6→v9、v9→v6、v6→v9 交替运行：

| 事件数 | v6 三次 ms | v9 三次 ms |
|---|---|---|
| 1,000 | 7.877 / 7.894 / 7.730 | 7.390 / 7.893 / 7.497 |
| 10,000 | 75.612 / 77.654 / 76.099 | 76.617 / 84.554 / 76.978 |

交替样本两版 1k 每次约 5.44–5.46 MB、10k 每次约 49.69–49.80 MB，总分配接近；其中包括同进程 miniredis，不是后端 RSS。每次约 38.9k/362.9k 分配也接近。

另做 3 秒 CPU profile，10k 分别为 v6 79.311ms、v9 76.217ms（带 profile 的数值不能与无 profile 直接作收益计算）。两者均主要出现在 JSON decode、系统调用、map/GC 等路径，未确认新的独立热点；profile 长度和采样数不同，不能直接比较绝对 CPU 毫秒。未由此归因某个函数造成候选慢样本。

**结论：没有证据支持“升级必然更快”，也不足以从第一组直接确认稳定退化。10k 慢样本是验收风险，不被后续较快样本抹去。** 这不替代真实 Redis 基准，不更改候选合并门槛。

复跑各版本时先确认工作区干净，保存生产/候选版本号，依次执行：

```powershell
go test ./internal/services -run '^$' -bench '^BenchmarkCurrentEventListRedis$' -benchmem -benchtime=1s -count=3 -timeout 120s
```

保留相同 Go/CPU/数据、交替顺序及全部原始结果；不要混用不同日期的基线或将计算阶段 p95 当作整个 HTTP 接口 p95。临时 profile 和测试二进制仅在本机临时目录，未提交仓库。

## 4. 接下来真正需要的验收条件

| 顺序 | 环境 / 输入 | 允许先做的检查 | 达到什么才算通过 |
|---|---|---|---|
| A | 非生产 MySQL，脱敏代表性数据和只读连接配置 | 版本、表引擎、已有索引、核心查询 EXPLAIN、连接池等待 | 记录实际执行计划与资源预算；索引 DDL 另行审核，不自动执行 |
| B | 与生产同版本/ACL 的专用 Redis | 候选分支 opt-in 烟测，再做告警/静默/CAS/WATCH/通知去重的隔离业务验收 | 正常/故障/断连/重连结果正确；同负载延迟/内存无不可接受回退；明确处置普通 cancel 限制 |
| C | Linux 构建及隔离运行环境、同组镜像 | 镜像构建、race、代理缓存/SSE、BFF→Agent→Gateway 断连、ICMP | 使用部署链路而非单元 fixture 证明行为；记录三镜像不可变 tag/digest、配置和回滚步骤 |
| D | 已授权的小规模负载与模拟通知接收端 | 逐级提高规则/事件/静默和并发，采集 CPU/RSS/连接/等待/延迟/失败率 | 与修改前同负载比较，正确性不退化；测试停止阈值事先确认，不对生产直接发压测 |

无环境时不能自动安装/迁移生产服务、创建真实静默、发送通知、轮换密钥或运行索引 DDL来填补证据。连接信息通过安全配置文件或已有凭据通道提供，不放在聊天与仓库。

## 5. 不盲目扩展的项目

- 当前列表索引、更多缓存、会话虚拟列表、审计流式编码、大批指标拆批：剩余成本存在，但需要先证明瓶颈和兼容方案，不把“仍与数据规模相关”等同于必须重写。
- 通知 outbox、审计保留期、历史字段迁移、腾讯语音协议和新的配额/功能：涉及业务与数据治理决策，不能借性能目标自行扩展。
- 普通 Redis cancel 限制不能用后台 goroutine 提前返回或关闭共享池“修复”；后续技术方案需要保留在途写入真实性和连接池隔离。

本次工作形成了新对照证据并修正总清单中的过时 Agent 版本。整体目标仍 active；没有把当前局部代码或文档检查视为完成全部验收。
