# 恢复事件归档：先持久化、幂等重试、条件清理

日期：2026-10-10。后端基线 `a0c88a9`，开发分支 `codex/recovery-archive`。前端和独立 Agent 无修改。

## 已确认的问题

原消费者先无条件 HDEL 缓存，再插入历史表；SQL 失败后没有可重试源数据。删除接口没有返回错误，也没有校验同一指纹下是否已换成新事件。简单调换两行仍不能解决“SQL 成功，Redis 失败，下一轮重复 INSERT”问题。历史表没有主键/唯一事件约束，直接增加唯一索引需要处理旧重复数据和大表迁移。

## 本批实现

1. 先在数据库事务内保存归档凭证和历史记录，两者共同提交/回滚；只有成功后才尝试删除恢复缓存。
2. 新增小表 `alert_archive_receipts`，`archive_key` 是版本化事件身份的 SHA-256，`owner` 是本次事务的随机标识。重复请求利用主键冲突保留首个 owner；读回 owner 判断是否需要 INSERT 历史，不依赖 MySQL `RowsAffected`/`clientFoundRows` 差异。
3. 身份由租户、中心、指纹、规则、事件 ID、首次触发时间组成。兼容事件 ID 为空但首次时间存在的旧事件；可变标签、通知时间、恢复时间不改变归档身份。同一事件首次成功保存的历史快照不被重试覆盖。
4. 不扫描历史表检查重复，不修改历史表结构，不回填/清理旧重复行；新增主键查询发生在凭证表。每个新归档多一条小凭证，不保存重复标签和正文。
5. Redis 先核对身份、恢复状态及恢复时间，再用原始 JSON CAS 删除，最多 4 次竞争重试。删除失败明确返回错误；新事件、已消失事件和状态改变都不继续本次恢复通知。并发只有实际删除者进入后续通知流程。
6. 数据库失败保留缓存；SQL 已提交但 Redis 失败时，下一轮幂等重试。一个轮次遇到存储失败后不对该中心其余恢复事件继续冲击故障存储，仍保留活跃告警候选。无效事件仅跳过自身，不阻塞其他正常恢复事件。
7. 历史保存透传请求取消并限制为 10 秒；跨中心/租户输入、状态矛盾及无可靠首次时间的记录不被直接归档删除，记录错误等待核查。

这是可靠性前置改动，并非单次归档 SQL 数减少。新流程增加凭证 INSERT/主键读取和 Redis CAS；收益是故障期间不丢历史、不重复累积历史数据、不对每条恢复事件重复冲击失败存储。没有生产吞吐提升比例结论。

## 升级条件（本批有新表）

- 服务启动会创建/校验 `alert_archive_receipts`，需要相应 DDL 权限；已有历史记录不迁移、不去重。
- MySQL 的 `alert_his_events` 和新凭证表必须都是 InnoDB。启动会读取表引擎并拒绝非 InnoDB，**不会自动转换历史大表的引擎**；新凭证表显式使用 InnoDB。SQLite 使用原有事务能力。
- 部署前只读检查：

```sql
SELECT TABLE_NAME, ENGINE
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN ('alert_his_events', 'alert_archive_receipts');
```

- 如发布账号没有建表权限，可由数据库管理员事先创建；以下仅是审核用 DDL，本轮未在生产执行：

```sql
CREATE TABLE IF NOT EXISTS alert_archive_receipts (
  archive_key VARCHAR(64) NOT NULL,
  owner VARCHAR(32) NOT NULL,
  PRIMARY KEY (archive_key)
) ENGINE=InnoDB;
```

- 已有同名表不能只凭 `IF NOT EXISTS` 判断正确，需要核实列和主键。凭证应与数据库历史一起备份恢复；不要单独清空凭证，否则旧任务重试可能产生重复历史。未来历史保留/清理方案需要同时定义凭证保留策略，当前不自动清理两者。
- Redis 继续需要 HGET/HDEL/EVALSHA/EVAL 权限。多副本应全部升级；旧副本仍使用无条件删除及非幂等 INSERT，混合版本没有完整保障。
- 回滚至 `a0c88a9` 镜像可以保留新增表，旧代码不会使用它，但会恢复原来的丢历史/重复风险。不要为了回滚删表。再次升级不会自动修复回滚期间产生的重复历史。

## 验证结果与限制

- SQLite：24 个并发调用者/重复请求只有一份历史和凭证；连接池为 1，验证并发调用幂等性，不等同于 MySQL 多连接锁竞争验证。
- 故障注入：历史 INSERT 失败时凭证一起回滚，重试后正常写入；取消/无效身份/未迁移凭证表不写历史。
- 租户、中心、事件 ID、首次时间变化分离身份；空事件 ID 的旧记录可重复处理；首次快照不被后续可变字段覆盖。
- MySQL 方言仅 dry-run 验证冲突 SQL 不更新 owner，没有连接真实 MySQL。
- miniredis：24 个并发删除只有一个成功者；读写之间注入同指纹新事件不会误删；损坏 JSON、Redis 故障、不同恢复时间、取消及持续 CAS 冲突均覆盖。
- 消费者测试覆盖 SQL 失败保留缓存且活跃告警继续、Redis 删除失败后再归档、只有删除者进入恢复通知、租户隔离和无效记录不影响其他归档。
- SQLite 启动迁移重复执行保留旧历史。消费者/缓存/仓库/客户端测试连续 10 次、后端既定相关包非缓存回归和相关包 `go vet` 通过。
- 后端二进制构建通过，产物仅位于本机临时目录，未部署。
- 未连接生产数据库/Redis，未执行大表迁移、真实 MySQL 并发、容器构建、生产压测或竞态检测；当前 Go 环境无 race 所需 C 工具链。

## 尚未解决

归档成功不等于恢复通知送达。删除成功后进程退出、删除响应丢失、后续静默读取失败或渠道失败，仍可能没有恢复通知；这需要持久化通知待办/对账以及渠道幂等策略，不能用数据库归档凭证冒充可靠投递。“只有删除者发送”仅减少并发重复尝试，不承诺跨 SQL/Redis/外部渠道恰好一次。

凭证与历史的人工不一致、切换前已有重复数据不自动修复；无首次时间的旧记录需要人工核查。规则缓存全量扫描、其他查询 provider、长会话/大列表和代理配置等整体性能待办继续保留。
