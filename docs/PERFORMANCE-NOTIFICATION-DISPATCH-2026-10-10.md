# 有界通知调度与消费者生命周期

日期：2026-10-10。后端基线 `3c4d296`，开发分支 `codex/notification-dispatch`。前端与独立 Agent 无变更。

## 代码证据与改动

- 原 `Consume.sendAlerts` 对所有规则/通知对象串行调用发送；任一慢渠道会阻塞后续独立组。现在每中心每轮最多 4 个组 worker，使用无缓冲通道传递任务，发送完全部已接收工作才进入升级阶段/下一轮。
- 普通和升级通知共享全进程 8 个发送处理槽位；槽位覆盖一个等级组的准备与发送。每个通知对象最多 4 个等级组 goroutine，避免异常等级值造成无限 goroutine。未引入额外队列服务、配置项或依赖。
- 排队期间不读取静默快照、不更新时间；拿到槽位后才准备，后续路由仍按上一批规则重新读取静默。取消等待不执行待处理工作，panic 也会释放槽位并记录错误。
- 每个并行通知对象拿到独立事件值副本，通知时间/认领时间/注释/值班人不再修改其他组共享的源指针。标签与嵌套配置保持只读，未为所有积压事件做 JSON 深拷贝；如果未来模板允许修改嵌套值，必须先调整复制策略。
- 空工作批次不创建发送 goroutine；不足 4 组时仅创建相应数量的 worker。任务不因队列满而丢弃，而是让生产循环等待可用 worker。
- 原 `Submit` 直接覆盖取消句柄，旧消费者仍运行。现在每个中心只有一个自有 worker，重复提交合并到最新配置并取消在途请求；旧轮次真实退出后才处理新配置，不把“发出取消”当作“已经停止”。
- Stop 后立即 Submit 也复用正在退出的 worker，避免双循环；异常只结束当前轮次，不再递归 Restart，因此旧任务无法在较新配置生效后重新启动自己。
- 消费者登记表独立于共享 ContextMap，StopAllConsumers 不再取消规则评估、LDAP 或值班表任务。停止日志明确是请求取消，在途任务仍需退出。恢复事件遍历也增加取消检查。

## 本地验证

- 100 组阻塞任务：同时在执行的组为 4，解除阻塞后全部完成；共享源事件的字段保持不变。
- 全局 8 个槽位占满时，第 9 个等待者可被取消，不能进入准备/发送；正常退出和 panic 后槽位均回收。
- 排队通知取消时无静默读取、无通知时钟写入、无 HTTP 发送；100 组待办在取消后不继续发送未开始的积压组。
- 真实本地 HTTP 模拟渠道：12 个通知对象共享源事件，先确认 4 个请求同时到达再放行，最终 12 次发送/时间校验全部完成，源字段不变。
- 旧轮次忽略取消、延迟退出并 panic；连续提交中间/最新版本，只启动最新版本，执行峰值保持 1。
- Stop/Submit、StopAll 与其他任务隔离、父上下文取消后拒绝新任务，以及单组 panic 不终止其他组均覆盖。
- 消费者测试连续 10 次通过；cmd、alert、internal、api、client、tools、provider、medium、oidc 相关包非缓存回归、消费者 `go vet`、后端二进制构建通过。没有运行带外部目标的 provider/test 示例包。
- 当前 `CGO_ENABLED=0`，未具备 Go race 所需 C 工具链，因此不能宣称竞态检测通过；以上是显式并发场景测试与代码检查。

以上验证的是并发上限、取消、引用隔离和实际本地发送，不是生产压测，也不能推导“生产快 4 倍”。没有运行真实通知渠道或访问生产。

## 兼容性与剩余边界

- 不改变接口、SQL 表、Redis 格式；只需更新后端镜像。保留前批 CAS 脚本权限要求。
- 8 是单进程上限，不是跨副本全局配额，也不是每秒请求限流。多个后端未启用选主时仍可能重复消费，尚未提供渠道级幂等投递。
- 槽位持有到该等级组完成，超大单组、多收件人、或多个慢渠道仍会占用容量；不通过固定整批超时丢掉尾部收件人。所有组等待结束后才启动本中心升级/下一轮，未声称消除所有队头阻塞或实现严格公平调度。
- 请求取消无法撤回已经送达外部系统的消息；部分旧 SQL/Redis API 不接受请求上下文，轮次退出仍可能等到底层操作超时。规则评估器自己的共享任务登记/重启问题仍需另批核查。
- 历史落库早于/晚于缓存删除、恢复通知可靠投递问题尚未完成；本批不引入“恰好一次”承诺。
- 回滚至 `3c4d296` 对应镜像无需数据迁移，但会恢复串行发送和旧消费者生命周期问题。合并/推送不代表生产已更新。

后续继续处理恢复事件持久化、规则维度扫描、其他 provider、长会话与部署代理；本批不代表整体性能目标完成。
